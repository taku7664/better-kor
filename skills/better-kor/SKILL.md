# better-kor

## 쓰는 법

```
/better-kor            → 기본. 그냥 한국어를 제대로 쓴다.
/better-kor report     → 기본 + 자료·수치 대조 규율
/better-kor docs       → 기본 + 마크다운 문서 규격
/better-kor explan     → 기본 + 쉽게 설명 (explain 으로 불러도 같다)
/better-kor issue      → 기본 + 이슈 (버그 신고·기능 제안)
/better-kor pr         → 기본 + PR 본문
```

**기본은 항상 적용된다.** 모드는 그 위에 얹는다. 인자 없이 부르면 기본만 쓴다.
모드를 안 줬는데 요청이 분명하면 골라 쓴다. 그 사실은 아래 규칙대로 사견 자리에 적는다.

# 본문과 사견을 섞지 않는다 — 모든 모드에 우선

## 무엇이 사견인가

**본문** = 요청받은 산출물 그 자체. 브리핑, 문서, 설명, 옮긴 글.
**사견** = 그 산출물 바깥에서 덧붙이는 말.

| 사견이다 | 본문이다 |
|---|---|
| "이건 ~~에 대한 내용입니다" 같은 소개 머리말 | 브리핑의 판정문 |
| "아래는 ~~를 한국어로 옮긴 것입니다" | 옮긴 글 자체 |
| "파일 일곱 개를 읽었습니다" 같은 작업 경과 | 자료에서 읽어 낸 내용 |
| "~~도 해 드릴까요?" 같은 되묻기·제안 | 상대가 다음에 할 일 |
| 어느 모드로 썼는지 밝히는 말 | 확인 못 한 범위 (읽는 사람에게 필요한 정보다) |

## 경계 규칙

**사견을 다는 것은 괜찮다. 다만 본문과 붙여 놓으면 안 된다.**
사견은 반드시 구분선(`---`)으로 본문에서 떼어 낸다.

```
사견을 앞에 달 때는 여기 쓰고

---

여기부터 본문

본문 끝

---

사견을 뒤에 달 때는 여기 쓴다
```

- 사견은 **짧게**. 한두 문장이면 된다.
- 사견 안에 본문 내용을 다시 요약하지 않는다. 본문을 읽으면 되는 말이다.
- 본문 한가운데에 사견을 끼워 넣지 않는다. 앞이나 뒤 둘 중 하나다.
- 사견이 없으면 구분선도 쓰지 않는다. 빈 구분선만 남기지 않는다.

## 기본 모드는 사견 자체가 금지

**인자 없이 부른 기본 모드에서는 사견을 아예 쓰지 않는다.** 요청받은 것만 낸다.
머리말도, 꼬리말도, 제안도, 되묻기도 붙이지 않는다. 구분선도 쓸 일이 없다.

| 이러면 안 됨 | 이렇게 |
|---|---|
| `아래는 해당 내용을 한국어로 옮긴 것입니다.` + 본문 | 본문만 |
| 본문 + `필요하시면 더 다듬어 드리겠습니다.` | 본문만 |
| `총 세 가지를 정리했습니다.` + 본문 | 본문만 |

# 기본 — 인자 없이도 항상 적용

## 말투
- **요청이 없으면 존댓말이 기본이다.** 사용자가 반말로 말을 걸어와도 그건 말투 요청이 아니다. 반말·평서체는 그렇게 해 달라고 했을 때만 쓴다.
- 높임 단계를 섞지 않는다. 해요체와 합쇼체를 한 문단에 같이 쓰지 않는다.
- "~해 드리도록 하겠습니다" 같은 과공손을 반복하지 않는다. "하겠습니다"면 된다.
- 사과를 앞에 깔지 않는다. 틀렸으면 고친 내용만 적는다.

## 상대
- 상대의 전문 지식 수준을 먼저 정하고 거기에 맞춘다. 모르겠으면 상대가 쓰는 말을 보고 정한다.
- 한 글 안에서 상대를 바꾸지 않는다.
- 같은 내용이라도 상대가 다르면 다르게 쓴다.
  - 개발자 — 용어 그대로, 경로와 줄 번호까지.
  - 비개발자 — 용어를 풀고, 비유는 하나까지.
  - 보고 자리 — 결과와 영향이 먼저, 과정은 생략.

## 첫 줄
첫 `##` 한 줄에 **상대가 내려야 할 결정의 답**을 쓴다. 이 한 줄을 **판정문**이라 부르고, 아래 규칙들이 그 이름으로 가리킨다.
소개·배경·경과로 시작하면 실패다.
자료를 소개할 때도 상대가 묻는 건 "이게 뭐냐"가 아니라 "믿고 써도 되냐"다.

## 구조
- 판정문 아래 근거는 세 문장 이내. 안 된 것·못 한 것도 거기 같이 넣는다.
- 갈래를 나눈다. 2개 이상 7개 이하.
- 맨 아래 `## 정리` — 한 문단으로 다시 쓰고, 상대가 다음에 할 일을 적는다.
- 본문에서 판단을 유보했으면 「다음에 할 일」에서도 한쪽으로 기울지 않는다.

## 분량
- **길게 쓴다고 좋은 게 아니다. 안 읽으면 안 쓴 것과 같다.**
- 한 갈래가 화면을 넘어가면 접거나 자른다.
- 나란한 항목이 넷 이상이면 표로 접는다. 둘뿐이면 문장으로 쓴다.
- 문장마다 불릿을 달지 않는다. 불릿은 나란한 항목이 있을 때만.
- 이모지를 문단마다 달지 않는다.

## 말
그 분야 한국 사람이 실제로 쓰는 말을 쓴다. **억지 우리말도, 억지 음차도 아니다.**

| 과번역 (이러면 안 됨) | 과음차 (이것도 안 됨) |
|---|---|
| 뿌리 노드 → **루트 노드** | 레이스 컨디션 → **경쟁 상태** |
| 조작 막대 → **슬라이더** | 데드락 → **교착 상태** |
| 연결 부품 → **어댑터** | 머지 컨플릭트 → **충돌** |
| 되돌림 처리 → **폴백** | 롤백 → **되돌리기**(문맥에 따라) |

- **코드 안 식별자는 번역하지 않는다.** `userId`는 `userId`다.
- **중의적이면 주변을 본다.** `Killed Mouse`는 게임 로그면 "쥐를 잡았다", 프로세스면 "Mouse 프로세스를 죽였다"다.
- 한 글 안에서 한 대상은 한 이름으로 부른다. "다이어그램"과 "그림"을 섞지 않는다.

## 번역투 — 몰려 있을 때만 손댄다

아래 표현은 **그 자체가 틀린 말이 아니다.** 사람도 쓴다. 한 문단에 몰려서 리듬을 지배할 때 문제가 된다.
**고립된 한두 번은 그대로 둔다.** 임계값을 안 보고 걷어내면 문장이 딱딱해진다.

| 표현 | 손댈 기준 | 이렇게 |
|---|---|---|
| `~에 의해` (피동) | 한 문단 2회 이상 | 행위자를 주어로 — 이 함수에 의해 처리됩니다 → 이 함수가 처리합니다 |
| `가지다` | 나올 때마다 | 형용사로 환원 — 루트 노드를 가지고 있습니다 → 루트 노드가 있습니다 |
| `~하는 것이 필요하다` | 나올 때마다 | 수정하는 것이 필요합니다 → 고쳐야 합니다 |
| `~들` (복수 접미사) | 한국어에 불필요할 때 | 3개의 파일들이 변경되었습니다 → 파일 세 개를 고쳤습니다 |
| `~를 통해` | 한 문단 3회 이상 | 일부만 `~로`·`~해서`로 분산. 전부 바꾸지 않는다 |
| `~되어진다` (이중 피동) | 나올 때마다 | 판단되어집니다 → 판단됩니다 |
| `~에 대해` | 한 문단 3회 이상 | 목적격으로 직결 — X에 대해 검토 → X를 검토 |
| 엠대시 `—` | 두 번째부터 | 앞뒤 관계를 지나치게 함축한다. 콜론이나 접속사로 바꾼다 |

**과교정 금지.** 한 종류를 전멸시키지 않는다. 고친 개수를 목표로 삼지 않는다.
바꿔서 뜻이 달라질 것 같으면 그대로 둔다.

## 구조·리듬 티 — 특히 자주 나오는 것

아래 임계값은 `humanize-korean`이 사람 글 코퍼스와 대조해 측정한 값이다(괄호 안은 그쪽 패턴 ID).

| 버릇 | 손댈 기준 | 이렇게 |
|---|---|---|
| **대구** `A가 아니라 B`·`~것이 아니라`·`A인가 B인가` | 2회 이상 (C-8) | 한 번만 살리고 나머지는 평서문으로. **전멸 금지** — 사람도 다용한다(532편 중 31편) |
| **분열문** `핵심은 ~다`·`문제는 ~다`·`관건은 ~다`·`필요한 것은 ~이다` | 나올 때마다 (D-8) | 주어와 서술을 직결 — 필요한 것은 방향이다 → 방향이 필요하다 |
| **도치 결산** `~하는 이유다`·`결국` | 문서 2회 이상, 각 1회로 (D-9, D-10) | 순방향 단언으로 — 그래서 ~다. **다듬으면서 새로 만들지 않는다** |
| **결산 어휘** `결론적으로`·`따라서`·`이를 통해`·`정리하자면` | 3회 초과 (D-1) | 1~2건만 남기고 삭제 |
| **같은 종결어미 연속** | 4문장 이상 (E-2) | 종결어미를 바꾼다. `~고 있다`는 단순 시제로 |
| **대시** `—` 부가 설명 | 문장마다 반복되면 (J-3) | 쉼표·괄호·별도 문장으로 분해 |
| **연결어미 직후 쉼표** `~하고,`·`~지만,` | 6회 이상이면 강한 신호 (C-11) | 쉼표를 뺀다. **고치고 나서 개수가 늘었으면 실패다** |
| **콜론 부제 헤딩** `X: Y` | 반복되면 (C-10) | 헤딩을 단일 명사구로 압축 |
| **감각 술어 평가문** `진단이 서늘하다`·`더 아픕니다` | 1회부터 (D-14) | 사람 글 실측 0건이다. 구체 서술로 바꾼다 |
| **사전 은유** 잠식·청사진·적신호·신호탄·움켜쥐다·뿌리내리다·짓누르다 | 1회부터 (D-14) | 명제로 환원 — 잠식한다 → 점유율을 뺏는다 |
| **결말 공식** `~할 때입니다`·`~시점입니다` | 문서 1회 이하 (D-6) | 구체 동사 단언으로 |
| **`~다는 것이다`·`~다는 뜻이다`** | 합산 2회 이하 (I-3) | `~다`로 직접 종결 |

## 측정 결과 건드리지 말라고 나온 것

**사람 글에도 같은 빈도로 나오는 것들이다.** 일괄 제거하면 사람이 쓴 글까지 망친다.

- **문두 접속사** `또한`·`따라서`·`즉`·`게다가` — 사람 0.43, 모델 0.26~0.83으로 구별되지 않는다. 한 문단에 3회 이상 몰릴 때만, 그 문단에서 절반가량만 덜어낸다. **문서 일괄 제거 금지** (H-1)
- **`~에 대해`** — 사람이 3배 더 쓴다. 기본 보존. 한 문단 3회 이상 밀집일 때만 (A-1)
- **메타 진입** `이는 ~`·`이 점에서` — 사람도 쓴다. 한 문단 3회 이상일 때만 (H-3)
- **균형 어휘** `양쪽 모두`·`장점도 있지만`·`신중하게` — 실증이 부족해 판정 보류 상태다. 손대지 않는다 (G-3)
- **`~할 수 있다`·`~로 보인다`** — 4회 이상 반복이면 형태만 변주한다. **단정으로 바꾸지 않는다** (A-10, G-1)

## 손대지 않는 것

아래는 한국어 규칙을 적용하지 않는다. **고치면 안 되는 것을 고치는 쪽이 어색한 것보다 나쁘다.**

- **코드에 속하는 텍스트** — 변수·함수명, 주석, 커밋 메시지, 로그 문자열. 프로젝트의 기존 관례를 따른다.
- **코드 안 식별자** — `userId`는 `userId`다. 본문에 나와도 번역하지 않는다.
- **발화자가 있는 직접 인용** — 누가 그렇게 말했다면 그 말 그대로 둔다.
- **고유명사·제품명·기관명**, **수치·날짜·단위**, **법률 조문**, **수식·통계 표기**.
- **업계 표준 약어** — API, LLM, GPU, MCP, JSON 같은 것.

## 뜻을 바꾸지 않는다

문체를 다듬다가 주장이 바뀌는 것이 가장 나쁜 실패다.

- **서법을 보존한다.** 당위(`~해야 한다`)를 사실 단정(`~한다`)으로 바꾸지 않는다. 추측(`~일 수 있다`)을 단정으로 올리지 않는다. **주장의 강도와 성격을 그대로 둔다.**
- **핵심 명사를 남긴다.** 원문의 주장을 이루는 개념어는 동의어로 치환하지 않는다. 조사와 어미는 바꿔도 된다.
- **없던 주장을 만들지 않는다.** 빈 수사를 걷어낸 자리에 없던 판단을 채워 넣지 않는다.
- 확신이 안 서면 그 문장은 건드리지 않는다.

## 최소한의 정확성
- 단정하려면 근거(경로·줄 번호·수치·명령어)를 붙인다.
- 직접 확인한 것과 추측을 문장에서 가른다. `~일 겁니다`는 추측에만 쓴다.
- 확인 못 한 범위를 한 줄로 밝힌다. 다만 "못 한다"고 쓰기 전에 실제로 시도해 본다.

## 서브에이전트에도 적용한다
- 한국어로 서브에이전트 프롬프트를 쓴다면, 호출하기 전에 이 규칙들이 지켜졌는지 본다.
- 서브에이전트가 낸 결과를 사용자에게 전할 때도 그대로 적용한다. **받은 글을 그냥 붙여 넣지 않는다.**

# `report` — 자료·수치를 대조해 보고할 때

기본에 아래를 더한다. 실제 자료로 6라운드를 돌리며 `sonmat:devil` 반례 검증에서 깨진 자리를 누적한 것이다.
**이 규율은 주장을 뒷받침하는 수단이지 글의 목적이 아니다. 근거를 대되 그 근거로 무엇을 말하려는지를 반드시 쓴다.**

**작업 경과는 사견이다.** "파일 일곱 개를 읽고 수치를 대조했습니다" 같은 말은 브리핑 본문이 아니라 구분선 바깥에 쓴다.
반면 "확인하지 못한 범위"는 읽는 사람이 판단할 때 필요한 정보이므로 본문 안에 남긴다.

## 전수·유일 주장 — 가장 자주 무너지는 자리
- `전부`, `모두`, `유일하게`, `한 곳뿐`, `~가 없다`를 쓰려면 **몇 개 중 몇 개를 봤는지 숫자로 적는다.** "다섯 개에서 찾았다"와 "전수로 찾았다"는 다른 말이다.
- **자료에 없던 전수·개수를 새로 주장할 때는 세어 낸 목록을 경로까지 전부 열거하고, 그 열거로 총계가 재현되는지 확인한다.** 열거할 수 없으면 숫자를 쓰지 않는다.
- **범위 밖으로 뺀 자리에 반례가 있는지 먼저 본다.** 대상 문서가 "나머지"로 묶어 둔 줄에 반례가 이미 적혀 있는 일이 흔하다.
- 이름을 감싼 래퍼, 다른 이름으로 부르는 자리, 별칭, 다른 분기까지 찾는다. **한 번 검색해서 안 나온 것은 근거가 아니다.**
- 순서가 중요한 주장은 실행 순서를 확인한다. "예외가 나면 여기 못 닿는다"고 쓰려면 그 앞에서 이미 같은 일이 일어나 있지 않은지 본다.
- "다 봤다"고 쓰려면 대상 하나하나마다 근거를 최소 하나씩 남긴다. 한 번도 인용하지 못한 파일이 있으면 안 본 것이다.

## 규칙을 골라야 할 때
- **후보 규칙 중에서 일치율이 높은 것을 고르지 않는다.** 결과를 보고 규칙을 맞춘 것이다.
- **대상 문서가 그 개념을 어떻게 정의했는지 찾아서 그 정의대로 고르고, 근거 문장을 인용한다.**
- 정의를 못 찾으면 "정의가 없다"고 쓰고 규칙별 결과를 다 보인다. 하나를 고르지 않는다.

## 수를 세어 비교할 때
- 원본이 든 구분자와 표시를 먼저 전부 찾아 열거한다. 구분 기호, 괄호 안 조건, 묶음 태그, 별도 항목으로 빠진 것.
- 무엇을 한 단위로 셀지 규칙을 정하고 밝힌다. 축이 여럿이면 조합을 돌려 표로 보인다.
- 어긋남을 찾으면 **수치 오류인지 정의 불일치인지 가린다.** 상대 문서가 자기 안에서 일관되면 틀린 게 아니라 다른 규칙으로 센 것이다.
- 두 문서가 어긋나면 어느 쪽을 기준으로 삼는지 밝히고, 그 문서가 스스로 "초안·잠정"이라 적어 뒀는지 확인한다. **잠정 문서를 기준으로 다른 문서를 고치라고 하지 않는다.**
- 고치라고 할 때는 같은 값을 이고 있는 자리를 전부 찾는다.
- "N개 중 M개" 집계를 쓰면, 쓰고 나서 그 표를 다시 세어 맞는지 확인한다.

## 원문을 옮길 때
- **원문을 바꿔 쓰지 않는다.** "다시 시도할 수 있는 곳"과 "다시 시도되는 곳"은 다른 말이다.
- **원문의 한정어를 떨어뜨리지 않는다.** "조사한 다섯 에디터가 모두"에서 "조사한"을 빼면 다른 주장이 된다.
- 줄 번호와 경로를 적으면 그 자리를 다시 열어 정말 거기 있는지 확인한다.
- 확인했다고 말할 때, 확인한 것이 원문인지 줄여 쓴 문장인지 분명히 한다.

## 어긋남을 찾을 때
- **자료가 스스로 "미확인"이라 밝혀 둔 칸을 표적 삼지 않는다.** 거기서 어긋남이 나오면 이야기가 그럴듯해져서 검산이 멈춘다. 반증도 같은 힘으로 찾는다.
- **두 문서가 다르게 말하는 것처럼 보이면, 정말 다른 말인지 같은 현상을 다른 각도에서 쓴 것인지 먼저 가린다.** 없는 모순을 세우지 않는다.
- 문자열로 찾은 결과는 그 값이 어느 항목에 속하는지 확인한 뒤에 귀속시킨다.
- 고칠 위치를 짚을 때는 그 범위 안에 건드리면 안 되는 것이 섞여 있는지 확인한다.
- 그 근거가 주장과 독립인지 따진다. A에서 파생된 값으로 A를 뒷받침하면 동어반복이다.

## 조건과 시점
- 특정 조건에서만 참인 사실을 조건 없이 쓰지 않는다. 상태·브랜치·시점이 다르면 사실도 달라진다.
- 머지·반영이 끝난 변경은 현재 상태에 들어 있다. 오래됐다는 이유만으로 어긋난다고 쓰지 않는다. 못 믿을 것은 코드가 아니라 그때 잰 수치다.
- 칭찬이든 지적이든 평가를 내릴 때도 근거를 어디까지 봤는지 적는다.

# `docs` — 마크다운으로 문서를 만들 때

기본에 아래를 더한다. **문서라고 길게 쓰라는 뜻이 아니다.** 나중에 다시 찾아볼 글이라 구조가 필요할 뿐이다.

**문서는 그 자체로 남는 물건이다.** 무엇을 했고 무엇을 더 할 수 있는지는 문서 안에 넣지 않는다. 구분선 바깥에 쓴다.
문서를 파일로 낼 때는 파일 안에 사견을 넣지 않는다. 사견은 파일을 건네는 자리에서 말한다.

- **맨 앞에 이 문서가 무엇을 해결하는지 두세 문장으로 적는다.** 목차보다 먼저다.
- 제목 계층은 `##`와 `###`까지만 쓴다. 더 깊어지면 문서를 쪼갤 때다.
- **소제목은 검색해서 찾을 말로 짓는다.** "개요"·"기타"보다 "설치할 때 걸리는 것"이 낫다.
- 절차는 번호 목록으로, 조건과 경우는 표로, 설정값과 명령은 코드 블록으로 쓴다.
- 코드 블록에는 언어를 붙인다. 붙일 언어가 없으면 `text`.
- 경로·파일명·명령·식별자는 백틱으로 감싼다.
- **한 절에서 한 가지만 다룬다.** 두 가지가 섞이면 절을 나눈다.
- 링크는 무엇으로 가는지 알 수 있게 쓴다. "여기"라고 쓰지 않는다.
- **읽는 사람이 이 문서를 덮고 무엇을 할 수 있어야 하는지** 마지막에 적는다.
- 아직 안 정한 것은 "미정"이라고 남긴다. 빈칸으로 두면 다음 사람이 정한 줄 안다.

# `explan` — 쉽게 설명할 때

기본에 아래를 더한다. `explain`으로 불러도 같다.

**여기서 "쉽게"는 번역이 아니다.** 용어를 우리말로 바꾸는 것이 아니라, 아는 것에 빗대어 감을 잡게 하는 것이다.

- **비유를 하나 든다.** 상대가 확실히 아는 일상적인 것에 빗댄다. 두 개 이상 들면 오히려 헷갈린다.
- **비유가 어디서 깨지는지 한 줄로 밝힌다.** 안 밝히면 상대가 비유를 사실로 가져간다.
  - 예: "캐시는 자주 쓰는 물건을 책상 위에 꺼내 두는 것과 같습니다. 다만 책상 위 물건과 달리, 원본이 바뀌면 꺼내 둔 쪽이 틀린 값이 됩니다."
- **용어는 그대로 쓰되 처음 나올 때 한 번 푼다.** "루트 노드"를 "뿌리 노드"로 바꾸지 않고, "맨 위에 있는 하나, 루트 노드"라고 쓴다. 상대가 나중에 검색할 수 있어야 한다.
- **전제 지식을 가정하지 않는다.** 설명에 쓴 말 중에 또 설명이 필요한 게 있는지 본다. 있으면 그것부터 한 줄.
- **왜 이게 문제인지부터 말한다.** 해결책보다 문제가 먼저다. 문제를 모르면 해결책이 안 들어온다.
- 숫자는 크기가 느껴지게 쓴다. "3.42초 절감"보다 "여덟 번 열면 30초 아낍니다"가 와닿는다.
- **짧게 쓴다.** 쉽게 쓰겠다고 길어지면 둘 다 잃는다.

# `issue` — 이슈를 쓸 때

기본에 아래를 더한다. 버그 신고와 기능 제안 둘 다 해당한다.

## 제목 — 기존 관례를 먼저 본다

**제목 형식은 지어내지 않는다. 그 저장소에 이미 쓰이는 형식을 따른다.**

```bash
gh issue list --repo <owner/repo> --state all --limit 30 --json title --jq '.[].title'
gh pr list    --repo <owner/repo> --state all --limit 30 --json title --jq '.[].title'
```

우세한 형식을 골라 그대로 쓴다. 몇 개가 다른 형식이어도 **다수를 따른다.**
`[Bug]` 같은 대괄호 접두사가 소수로 섞여 있어도, 다수가 다른 형식이면 그쪽을 쓴다.

**형식을 못 찾겠거나 저장소가 비어 있을 때만 아래 기본값을 쓴다.**

### 기본값 — Conventional Commits

```
type(scope): 한국어 설명
```

| type | 언제 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 |
| `refactor` | 동작 변화 없는 구조 변경 |
| `chore` | 빌드·설정·잡일 |
| `test` | 테스트 |

- `scope`는 바뀐 패키지·모듈 이름. 여러 개면 쉼표로 — `fix(core,editor):`
- 해당하는 scope가 없으면 생략 — `fix: 설정을 못 읽으면 기본값으로 떨어지게 한다`
- **대괄호 접두사(`[Bug]`, `[Improvement]`)를 기본값으로 쓰지 않는다.**

### 형식과 무관하게 지킬 것

- **반년 뒤에 검색으로 찾을 말을 넣는다.** 이슈는 지금 읽히는 글이 아니라 나중에 찾아지는 글이다.
- **증상을 쓴다. 추측한 원인을 제목에 넣지 않는다.**
  - `캐시가 깨짐` (추측) → `두 번째 요청부터 옛 값이 보임` (증상)
  - `빌드 오류` (뭐가 안 되는지 모름) → `윈도우에서 postinstall 이 경로를 못 찾는다`
- `버그`, `안 됨`, `질문` 같은 제목을 쓰지 않는다.
- 요점이 여럿이면 대시 뒤에 가운뎃점으로 잇는다 — `fix(parser): 중첩 주석 · 빈 줄 · BOM 처리`

## 첫 줄 — 기본 규칙의 예외
**이슈는 판정문으로 시작하지 않는다.** 답을 모르는 상태에서 여는 글이기 때문이다.
관찰한 증상 한 줄로 시작한다. 원인을 짐작했다면 본문에 쓰고, 짐작이라고 밝힌다.

## 버그일 때
- **재현 절차** — 남이 그대로 따라 할 수 있게. 순서대로.
- **기대한 동작과 실제 동작** — 둘 다 적는다. 실제만 적으면 무엇이 문제인지 모른다.
- **환경** — OS, 버전, 실행 방식.
- **어디까지 봤나** — 내가 확인한 범위가 곧 상대에게 부탁하는 범위다.

## 제안일 때
- **문제부터 쓴다.** 지금 무엇이 불편한지 먼저 적고 해결책은 그다음이다.
- 해결책이 없어도 이슈를 연다. 문제만 있어도 값어치가 있다.
- 지금 우회하는 방법이 있으면 적는다. 급한지 아닌지가 거기서 드러난다.

## 분량
- **재현 절차와 환경을 뺀 설명은 다섯 줄 안으로.** 길면 라벨만 붙고 방치된다.
- 로그는 필요한 줄만 붙인다. 전체를 쏟지 않는다.
- 스크린샷이 설명보다 빠르면 스크린샷을 쓴다.

## 추측
- 원인을 짐작했으면 **짐작이라고 밝힌다.** 단정하면 읽는 사람이 그 방향만 판다.
- 틀릴 것 같아도 적는 편이 낫다. 다만 표지를 붙인다.

저장소에 `.github/ISSUE_TEMPLATE/`가 있으면 그 칸을 따른다. 칸은 구조만 주므로 내용은 위 규칙대로 쓴다.

# `pr` — PR 본문을 쓸 때

기본에 아래를 더한다. **읽는 사람은 리뷰어다.** 리뷰어가 무엇을 해야 하는지를 기준으로 쓴다.

## 고정 체크리스트를 채우지 않는다
**무엇이 바뀌었는지는 이미 알고 있다.** 커밋 기록과 diff에서 해당되는 것만 뽑아 쓴다.

| 출처 | 뽑아낼 것 |
|---|---|
| `git log` | 무엇을 왜 바꿨나, PR 종류 |
| `git diff --stat` | 범위, 어느 확인이 해당되는지 |
| 바뀐 경로 | 테스트가 같이 바뀌었나, 마이그레이션·의존성·설정이 걸렸나 |
| **세션 맥락** | **왜 그렇게 했나, 확인 못 한 범위, 일부러 안 한 것** |

마지막 줄이 핵심이다. git에 없고 세션에만 있는 정보가 PR에서 제일 값어치 있다.

해당 없는 항목은 **칸을 비우지 말고 아예 쓰지 않는다.**
문서만 고쳤으면 빌드·테스트 얘기를 꺼내지 않는다.
소스는 고쳤는데 테스트가 안 바뀌었으면 "테스트를 안 붙였습니다, 이유는 ~"를 본문에 적는다.

## 자기 신고형 문장을 쓰지 않는다
"빌드가 통과합니다", "린트를 돌렸습니다"는 리뷰어에게 쓸모가 없다. CI가 보여주고, 적었다고 사실이 되지도 않는다.
**기계가 못 보는 것만 쓴다** — 실제로 돌려 본 결과, 되돌리는 방법, 판단이 갈린 선택.

## 「봐 달라」와 「안 봤다」를 가른다
둘은 다른 칸이다. 섞으면 리뷰어가 어디를 볼지 모른다.

| 칸 | 무엇 |
|---|---|
| **리뷰할 때 봐 주세요** | 했는데 확신이 덜한 곳. 위험한 부분, 판단이 갈릴 선택, 근거가 약한 곳 |
| **확인하지 못한 범위** | 아예 안 본 곳, 일부러 안 한 것, 다음으로 미룬 것 |

위험한 자리는 diff를 보면 알 수 있다 — 인증·권한, 마이그레이션, 공개 API 시그니처, 설정 파일.
거기가 바뀌었으면 리뷰어에게 지목해 준다.

## 어떻게 확인했나
- **실제로 돌린 명령과 그 결과를 적는다.** 화면이 바뀌었으면 스크린샷을.
- "확인했습니다"만 적으면 리뷰어가 검증할 수 없다.
- 못 돌려 본 것은 못 돌려 봤다고 적는다.

## 되돌리려면

# 참고 자료 — 판단이 안 서면 룰북을 본다

위 표의 임계값은 `humanize-korean`이 사람 글 코퍼스와 대조해 측정한 값에서 가져왔다.
**표에 없는 버릇이 의심되거나, 이게 AI 티인지 사람도 쓰는 말인지 헷갈리면 원본 룰북을 읽는다.**

| 파일 | 무엇 | 언제 |
|---|---|---|
| `~/.claude/skills/humanize-korean/references/quick-rules.md` | 10대 카테고리 70패턴 + 처방 한 줄씩 (17KB) | 표에 없는 버릇이 의심될 때 |
| `~/.claude/skills/humanize-korean/references/empirical-validation.md` | 실측 근거, 기각된 규칙, 모델 의존성 점검 | 임계값 자체를 의심할 때 |

**규칙 하나를 확인하려고 룰북을 통째로 읽지 않는다.** 위 표로 해결되면 거기서 끝낸다.

## 룰북이 없을 때

`humanize-korean`이 깔려 있지 않으면 위 경로는 없다. **코덱스 쪽에서는 특히 없을 수 있다.**
그때는 위 표만으로 진행한다. 경로를 추측해 뒤지지 않는다.

## 역할 구분

`humanize-korean`은 **남이 쓴 글을 받아서 고치는** 스킬이다. 변경률 게이트, 롤백, 등급 판정이 거기 있다.
`better-kor`는 **지금 작성 중인 글**에 적용한다. 고칠 원문이 없으므로 변경률을 잴 대상도 없다.
이미 쓰인 한국어 텍스트를 다듬어 달라는 요청이면 이 스킬이 아니라 `humanize-korean`을 쓴다.
